# 第二批：个人歌单、事务幂等和聊天历史

本批对应开发清单第 6、7、8 项。密码存储、注册登录的密码逻辑没有改动；LangChain4j 仍为 0.36.2。业务服务已可供后续经确认的 Agent 操作复用，本批尚未接入 Agent 写工具或确认卡片。

## 用户使用

用户端侧栏和头像菜单均有“我的歌单”，地址为 `/my-playlists`，管理详情为 `/my-playlists/{id}`。

- 创建、编辑名称/介绍/风格、公开或私有、删除、按歌名或歌手搜索并添加歌曲、移除歌曲、播放。
- 新建默认私有；公开后会进入公共列表、搜索和推荐。原有平台歌单保持公开，由管理端维护。
- 用户只能修改自己创建的歌单。私有歌单的内容、收藏和评论入口都受归属校验；管理员平台维护接口也不能误改个人歌单。
- 账号或页面切换后清空个人页面状态，忽略旧请求的迟到响应；侧栏收藏也按账号及请求版本隔离，旧收藏/取消收藏的响应不能修改新账号列表。

API 合约与限制见 [phase2-playlist-api.md](phase2-playlist-api.md)。创建和批量加歌最多携带 100 个歌曲 ID。

## 事务与幂等

`PersonalPlaylistService` 负责普通 HTTP 与未来 Agent 共用的业务逻辑。身份只取后端验证过的上下文，客户端不能指定用户 ID。后续异步 Agent 接入仍需显式传播可信身份上下文，不能假设请求 ThreadLocal 自动跨线程。

创建请求携带 `Idempotency-Key`，由 `(user_id, request_key)` 唯一键和请求内容摘要识别重试。相同请求返回原歌单，内容不同返回 409，已删除歌单的旧请求返回 410，防止重试意外重新创建。回执、歌单与初始歌曲绑定同事务提交，任何步骤失败都回滚。

加歌使用歌单行锁和既有 `(playlist_id, song_id)` 联合主键；收藏使用新增的两项唯一索引和数据库原子 upsert。重复收藏、取消收藏、加歌和移除均为幂等操作。收藏/评论写入先锁定并检查歌单可见性，避免与转为私有的操作发生校验竞态。收藏歌单列表不复用可能包含过期可见性的缓存。

## 聊天历史

完整记录按稳定消息 ID 追加到 `chat_messages`，模型上下文独立保存到 `ai_chat_state`，窗口上限仍为 20 条。窗口裁剪不再删除历史。历史追加和窗口更新同事务，系统提示词不会反复写入。

同一会话只允许一个运行中的生成请求，生成期间再次生成或清空返回 409。数据库租约支持多实例；每次写入都检查运行令牌和有效期，迟到回调不能覆盖新请求，也不能恢复已清空的记录。JVM 只保留当前请求的窗口，不保留无限增长的会话缓存。

详细语义与已有记录兼容说明见 [phase2-chat-history.md](phase2-chat-history.md)。旧实现此前已删除的历史无法恢复；供应商已接收的模型请求仍可能在应用取消后完成并计费。

## 迁移与本地状态

上线顺序：先迁移数据库，再更新/重启后端，最后更新用户端。其他环境按以下顺序执行 MySQL 8 脚本：

1. `sql/phase2_personal_playlists.sql`
2. `sql/phase2_favorites_migration.sql`
3. `sql/phase2_chat_migration.sql`

三份脚本都可重复执行。收藏脚本发现历史重复或异常资源类型时会中止，不擅自删除数据。MySQL 的 DDL 自动提交；如中途失败，修正问题后可以继续执行。既有级联外键不兼容资源字段上的 CHECK，因此保留外键、分别建立收藏唯一索引，由业务写入固定收藏类型及对应资源列。

2026-10-12 已在本机 MySQL 8.0.31 的 `vibe_music` 上执行迁移并验证再次执行。保留 17 个平台歌单、155 条收藏和 76 条既有聊天记录。相关原表备份位于已被 Git 忽略的 `target/phase2-before-20261012-021024.sql`。本次没有重启现有后端进程、提交 Git 或部署远端服务；运行中的后端需要重启加载新代码。
