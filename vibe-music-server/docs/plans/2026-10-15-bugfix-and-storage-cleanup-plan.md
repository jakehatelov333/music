**A、B：权限和会话设计**

关闭 `/admin/register` 路由并移除其免登录配置，避免只在前端隐藏按钮。现有管理员登录不受影响，不在这次修复中新增管理员开户产品功能。

本人资料更新只允许写入用户名、手机号、邮箱、简介等既有资料字段。保留旧 DTO 的 `userId` 兼容正常客户端：缺省或等于本人可以接受，其他 ID 返回 403；最终实体主键必须显式取认证上下文。管理员编辑用户保留“选择目标用户”的独立权限语义。

为用户账号增加单调递增的 `auth_version`，新用户 token 携带当前版本。统一认证服务同时检查 JWT、Redis 会话、用户存在性、启用状态及版本匹配。禁用与版本递增、改密/重置密码与版本递增必须在各自同一数据库事务中完成；重新启用不回退版本。删除账号后，所有旧 token 因账号不存在而失效，安全性不依赖 Redis 删除是否成功。普通退出仍仅退出当前会话。

旧用户 token 没有认证版本时要求重新登录一次，不保留“无版本 token 继续可用”的长期旁路。旧 Redis key 自然到期，不扫描/批量删除 key。管理员 token 按管理员认证规则处理，不强行套用用户版本字段。统一裸 token 和 `Bearer` 格式的解析。

不能仅修 `LoginInterceptor`：歌曲列表/推荐/详情、歌手详情、专辑、搜索中直接解析 token 的个性化分支也要改用统一验证结果。无 token 时维持公开浏览；携带失效 token 时返回明确的 401，客户端清理登录态并允许重新匿名浏览，避免请求循环或页面卡死。

**C：共享媒体与可靠清理设计**

对象身份采用规范化的 `(bucket, object_key)`，不以完整访问域名或歌曲名作为身份。兼容已有 localhost/127.0.0.1、历史路径前缀、中文、空格、百分号编码及字面 `+`。只解析明确属于配置桶的地址；不能把任意外部 URL 路径误当成本桶 key。数据库 URL 路径中的 `+` 不转换为空格。

新增媒体对象登记和清理任务两个独立概念：

| 概念 | 需要记录的内容 | 核心约束 |
| --- | --- | --- |
| 媒体对象登记 | 桶、完整 key、状态、上传会话、创建/到期时间、必要的对象校验信息 | 一个对象身份只有一条登记；新上传使用全新 key，禁止复用已删除的 key |
| 媒体清理任务 | 来源业务操作、对象身份、原因、状态、尝试次数、下次执行时间、执行租约/代次、脱敏错误 | 每条任务只指向一个明确对象；同一业务操作重复执行不会重复入队；不依赖已删除用户/歌单的外键 |

仓库现有迁移所定义的 `tb_account_cleanup_task`（当前数据库尚缺失）的唯一键是 `(user_id, resource_type)`，同一用户多个封面会覆盖彼此，不能直接把它改造成“一个用户多个封面共用一条记录”的队列。补齐该结构并新增通用 `tb_media_cleanup_task`。对于其他已经部署此表且存在未完成账号/头像任务的环境，需兼容接管；旧头像任务转交后只由一个 worker 处理，避免两套逻辑竞争。当前库不存在待转交的旧表记录。

业务删除/替换的顺序固定为：同一数据库事务内读取旧引用、变更业务数据、保存清理任务；事务提交后才允许执行外部删除。`afterCommit` 可以用于加快唤醒，但任务可靠性必须来自数据库，不能只保存在进程回调中。任务保存失败应回滚本次业务删除，不允许“记录已删、清理意图也丢失”。

worker 执行前检查全部 7 类媒体引用，包含停用歌手、草稿专辑、私有歌单和默认封面。仍有引用时将该任务结束为“保留”，等最后一个引用解除时由新的业务操作产生清理任务。

并发规则：新增/替换媒体引用的所有入口和 worker 都锁定同一媒体登记行。worker 在锁内重新核对引用，确认没有引用才将对象标记为 `DELETING` 并提交；随后进行 MinIO 删除，不在网络调用期间持有长事务。绑定方不能引用 `DELETING/DELETED` 对象。自动选歌单封面、专辑继承歌曲封面等隐式绑定入口也必须遵守这条规则。多对象业务操作按稳定顺序加锁以降低死锁风险。

任务状态建议为 `PENDING → RUNNING → SUCCEEDED`；临时失败进入 `RETRY_WAIT`，按退避时间重试；达到上限进入 `FAILED`，保留人工处理入口；仍有引用进入 `RETAINED`。`RUNNING` 具备租约和执行代次，旧执行者不能覆盖新领取者的结果。对象不存在视为删除成功，超时后的重复执行保持幂等。每次删除调用只使用一个完整对象 key，不使用前缀、通配符或多对象删除 API。

**D：统一账号删除设计**

自助注销和管理员删除复用统一账号删除服务，调用入口分别负责权限验证。事务内先锁定账号，收集用户头像和个人歌单自定义封面，在外键级联之前保存每个对象的清理意图；再删除反馈、无外键聊天记录/会话/任务指标，最后删除用户。收藏、歌单等可继续利用已确认的外键级联规则。

默认歌单封面不是该歌单独占文件，不能直接删除。自定义封面即使被错误或历史数据共享，也会被统一引用检查保护。共享资源是否可删由当前引用决定，不只靠 `cover_is_custom` 标志。

现有多账号删除入口保持数据库整体成功或整体回滚语义，按固定 ID 顺序锁定账号；每个待清理文件仍是一条独立任务。这次修复不在真实数据上执行多账号删除验收。

自助注销保留 `accountDeleted / cleanupPending` 语义。管理员端也要区分“账号删除失败”和“账号已删除、附件仍待清理”，避免用户误认为删除没有发生而反复操作。账号删除后旧 token 的拒绝由账号有效性检查保证，不依赖外部清理成功。

**E：上传、提交和暂存设计**

上传前完成身份、目标记录存在性及文件校验。正式对象写入前先生成不可复用的新 key，并登记上传会话与对象，这样进程在 PUT/COPY 成功后崩溃，也能找回需要处理的文件。

单曲提交涉及的新歌手、专辑、歌曲、歌手关系和媒体状态，应纳入同一个数据库事务。明确区分“尚未提交失败”和“提交后组装响应失败”：后者只能返回可恢复的错误/重新读取已提交结果，绝不能删除已提交对象。以上传会话作为幂等收据，相同上传重复确认返回同一歌曲/专辑结果，避免响应丢失后重复建库。

头像/封面替换时，新对象上传成功但数据库更新失败，只回收本次新对象；旧对象仍受原引用保护。旧对象清理任务与业务更新必须在同一数据库事务中持久化，提交成功后才允许执行删除。补偿操作同样采用持久任务，不能只在 `catch` 中尝试一次后记日志。

单曲和专辑统一采用持久会话状态：`OPEN → COMMITTING → COMMITTED`，或 `OPEN → CANCELLED/EXPIRED`。取消、过期与提交通过条件更新竞争，不能同时成功。`COMMITTING` 使用租约；崩溃恢复时先核对已提交业务结果，再决定恢复或清理。Redis 会话不存在不等于文件可立即删除，专辑静态 `SESSIONS` 的无限期回退应移除。

当前单曲清理阈值为 24 小时、Redis 会话却保留 48 小时，专辑会话也是 48 小时，存在“界面仍可提交、后台已经清理”的冲突。推荐以现有会话期限为准，将单曲和专辑可提交窗口统一为 48 小时，并在响应中返回准确 `expiresAt`；过期后进入清理等待而非继续允许提交。上线时单独核查既有草稿，不延长已过期或文件已经不完整的会话。

若预签名 PUT 地址尚未失效，客户端可能在取消后继续上传。最终清理时间不得早于该签名的最晚有效时间加缓冲；持久登记应覆盖已发出的对象 key，避免晚到上传重新产生孤儿。清理失败时保留任务，成功后才移除相关 Redis 索引/会话缓存。

**部署、观察和回滚**

先备份数据库并验证迁移，新增表和列部署在新逻辑之前。媒体登记回填只依据已核实对象与当前引用，标记为可用，不把历史候选自动入队。生产清理 worker 初始关闭；新代码覆盖所有媒体写入口后，先运行只记录判断、不删除的观察模式，确认共享引用判断正确，再开启逐对象消费。

避免新旧实例混合处理认证和媒体操作：旧代码仍可能接受失效 token 或直接删文件，不能依靠新 worker 来弥补。上线切换时应暂停相关写入口或使用明确的维护窗口，完成实例切换与媒体回填复核后再开放。回填与放开写入之间必须补齐增量，不能把初次审计的 989 当成未来永远不变的数量。

记录任务成功、保留、重试和耗尽数量，监测最旧待处理任务年龄、身份校验失败和缺失对象数；日志不记录密码、原始 token 或存储凭据。任务耗尽必须可查询并精确重试。

出现异常时先关闭清理 worker，保留清理队列和已迁移结构；可以回滚到经过安全修复的上一版本，不能直接恢复已知会误删文件或放行旧会话的版本。数据库迁移优先保留新增结构，不通过删表/删列回滚。对象若已被删除只能从备份恢复；数据库回滚本身不能恢复对象，因此上线前的观察和隔离验证必须完成。
